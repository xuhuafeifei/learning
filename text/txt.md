# 从文字到向量：一文读懂 Embedding 模型的原理、演进与应用

## 引言：当机器开始“理解”文字

你有没有想过，当你对 ChatGPT 说“帮我找一段关于猫的文本”，它是怎么在浩如烟海的资料里找到相关内容的？它并不像人类那样逐字阅读，而是把文字变成了一串数字，然后在数字的世界里做比较。

这背后支撑的技术，就是 **Embedding（嵌入）**。它做的事情听起来很朴素：把一段文本映射成一串固定长度的数字。但正是这个看似简单的操作，构成了现代 AI 理解语言的基石。无论是搜索引擎、推荐系统、问答机器人，还是最近火热的 RAG（检索增强生成），底层都离不开 Embedding。

这篇文章会从零开始，带你理解 Embedding 模型到底是什么、怎么工作的、为什么有效，以及它和当下的大语言模型（LLM）之间到底是什么关系。读完你不仅能理解原理，还能明白为什么你写代码时调用 `getEmbeddingFor(text)` 能得到一个向量，以及那个向量到底意味着什么。

## 一、为什么文字需要变成数字

计算机只认识数字。所有关于文字的处理，最终都要落到数字上。但“把文字变成数字”有很多种做法，不同做法决定了机器能理解到什么程度。

最古老的做法是**编码**，比如 ASCII 码把字母 `A` 变成 `65`，`B` 变成 `66`。这种编码的问题在于，它只是给每个字符分配了一个编号，编号之间没有任何语义关系。`65` 和 `66` 相邻，仅仅是因为 `A` 和 `B` 在字母表里相邻，而不是因为它们在语义上相似。

另一种做法是**独热编码（One-Hot Encoding）**。假设词表里有 10000 个词，每个词用一个 10000 维的向量表示，其中只有一个位置是 1，其余全是 0。这样每个词都是独立的，互不干扰。但它也有致命缺陷：任意两个词的向量都是正交的，余弦相似度永远是 0。也就是说，机器无法知道“猫”和“小猫”是相关的。

这两种做法的共同问题是：**它们只编码了符号身份，没有编码语义**。而 Embedding 要解决的，正是这个问题。

## 二、Embedding 的核心思想：把语义铺进高维空间

Embedding 的基本思路是：**用一个低维、稠密的向量来表示一个词或一段文本，并且让这个向量在空间中的位置反映它的语义。**

“低维”是相对于独热编码而言的。独热编码的维度等于词表大小，动辄几万；而 Embedding 的维度通常是 128、256、768、1024 这样的量级，小得多。“稠密”意味着向量里几乎每个位置都有非零值，而不是只有一个 1。

更重要的是，这个向量不是随便分配的，而是通过训练学出来的。训练的目标是：**语义相近的文本，向量在空间中的距离也要相近。**

这样一来，语义关系就被“铺”进了向量空间的几何结构里。比如：

- “猫”和“小猫”的向量夹角很小
- “国王”减去“男人”再加上“女人”，结果约等于“女王”
- “今天天气真好”和“阳光明媚”的余弦相似度会很高

这些都是真实存在过的经典例子。它们说明，Embedding 空间不是一个随机的数字堆，而是一个保留了语义结构的几何空间。

## 三、从词到句：Embedding 的三个层次

Embedding 技术并不是一步到位发展到今天的，它经历了从词到句、从静态到动态的演进。

### 1. 静态词向量：Word2Vec 与 GloVe

2013 年，Google 提出了 **Word2Vec**，这是 Embedding 技术的里程碑。它用两种训练方式（CBOW 和 Skip-gram）让模型学会：**一个词的含义，由它周围的词决定。**

比如“猫”经常出现在“喵”“毛”“宠物”附近，模型就逐渐把“猫”的向量推向这些词的向量附近。训练完成后，每个词都有一个固定的向量，而且语义相近的词会聚在一起。

但 Word2Vec 有一个明显的问题：**每个词只有一个向量，无法处理一词多义。** “苹果”在“吃苹果”和“苹果发布会”里，词义完全不同，但 Word2Vec 给出的向量是一样的。GloVe 用全局共现矩阵改进了一部分效果，但本质上仍是静态词向量，无法解决多义问题。

### 2. 动态上下文向量：BERT 与 Transformer

2017 年，Transformer 架构横空出世。它最大的创新是**自注意力机制（Self-Attention）**，能让每个词在处理时“看”到句子里的其他词，并根据相关性动态调整自己的表示。

2018 年，BERT 基于 Transformer 的编码器结构，第一次真正实现了**上下文相关的词向量**。在 BERT 里，“苹果”在“吃苹果”和“苹果发布会”里会得到不同的向量，因为它会分别和“吃”或“发布会”产生更强的关联。

但 BERT 输出的是每个 Token 的向量，而不是整句的向量。要做句子级 Embedding，还需要一步**池化**。

### 3. 句子级嵌入：Sentence-BERT 与专用模型

2019 年，Sentence-BERT（SBERT）提出用**孪生网络**结构训练句子级嵌入。它把两个句子分别送入 BERT，得到各自的句向量，然后用对比学习让相似句子的向量靠近、不相似句子的向量远离。

这标志着 Embedding 从“词级”正式走向“句级”和“段级”。今天的 `nomic-embed-text`、`BGE`、`text-embedding-3` 等模型，都是这一路线的产物。它们的目标很明确：**输入一段文本，输出一个能代表整段语义的向量。**

## 四、Embedding 模型的工作流程

一个典型的句子级 Embedding 模型，处理流程可以拆成四步。

### 第一步：分词（Tokenization）

模型不直接读句子，而是先把文本切成 Token。英文里 `"playing"` 可能被切成 `["play", "ing"]`，中文里 `"我爱吃苹果"` 可能被切成 `["我", "爱", "吃", "苹果"]`。每个 Token 对应一个整数 ID。

这一步本身不产生语义，只是把文本变成一串整数，方便后续查表。

### 第二步：查嵌入表

模型内部有一张巨大的**嵌入表**，形状是 `[词表大小, 向量维度]`。每个 Token ID 去表里查出自己对应的那行向量，得到一个初始向量。

但这时候的向量还只有词本身的含义，没有上下文。`"苹果"` 在“吃苹果”和“苹果发布会”里查出来的初始向量是一样的。

### 第三步：上下文编码

这串初始向量会送入 Transformer 编码器。自注意力机制会让每个 Token 去“看”句子里的其他 Token，并根据相关性调整自己的表示。

在“吃苹果”里，`"苹果"` 会更多和 `"吃"` 关联；在“苹果发布会”里，它会和 `"发布会"` 关联。经过多层这样的交互，每个 Token 的向量就融合了上下文信息。

### 第四步：池化

最后，把这一串 Token 向量压缩成一个向量。常见做法有三种：

- **CLS 池化**：取句子开头特殊 `[CLS]` Token 的输出向量（BERT 常用）
- **均值池化**：把所有 Token 向量按维度求平均（很多句向量模型用）
- **注意力池化**：用一个小网络学习怎么加权平均

最终得到的这一个向量，就是整段文本的 Embedding。你代码里 `context.getEmbeddingFor(text)` 返回的 `embedding.vector`，就是池化后的结果。

## 五、为什么语义相近的向量距离也近

这完全是**训练目标**决定的。训练时，模型会看到大量“相似文本对”和“不相似文本对”，然后被要求：

- 相似文本的向量**靠近**
- 不相似文本的向量**远离**

常用的损失函数有**对比学习损失（Contrastive Loss）**、**Triplet Loss** 等。经过千百万次调整，模型逐渐学会把语义结构“铺”进这个高维空间里。

正样本对可以来自很多地方：同一句话的两个不同表述、问答对、标题和正文、翻译对等。负样本对则通常是随机抽取的不相关文本。模型在不断区分正负样本的过程中，学会了什么样的文本应该靠近、什么样的应该远离。

## 六、Embedding 与 LLM：同一棵树上的两根枝

很多人第一次接触 Embedding 时会觉得：“这不就是大模型吗？”这个观察非常准确。**Embedding 模型和 LLM 在底层确实是同一套东西。**

它们共享相同的组件：Tokenizer、嵌入表、Transformer 架构、自注意力机制。可以说，Embedding 模型就是一个“阉割版 + 改造版”的 LLM。

但它们在四个关键点上不同。

**第一，输出不同。** LLM 输出的是下一个 Token 的概率分布，最终生成一段文本；Embedding 模型输出的是一个固定长度的向量，不生成任何文字。

**第二，架构方向不同。** LLM 主要用 Transformer 的 Decoder（因果注意力，只能看前面的词），因为要逐字生成；Embedding 模型主要用 Encoder（双向注意力，能看前后文），因为要理解整句语义。

**第三，训练目标不同。** LLM 预测下一个词，训练完就会“说话”；Embedding 模型做对比学习，训练完只会“判断两段文本像不像”。

**第四，池化层不同。** LLM 不需要池化，它要的是每个位置的输出；Embedding 模型最后要把整句压缩成一个向量，所以有池化步骤。

一个直观的比喻：把 Transformer 想象成一台文本理解机器。LLM 是在机器后面接了一个“文字生成器”，让它根据理解结果往外吐字；Embedding 模型是在机器后面接了一个“压缩器”，把理解结果压成一个向量。机器本体是一样的，只是后面接的东西不同。

最近几年，这两条路在互相靠拢。LLM 也能做 Embedding，比如用 GPT 系列模型取最后一层隐藏状态；Embedding 模型也能生成，比如 T5、BGE-M3 既能嵌入也能生成。你用的 `nomic-embed-text-v1.5`，本质上就是一个被改造过的小型 LLM，保留了 Transformer 的理解能力，但把输出从文字换成了向量。

## 七、Embedding 的典型应用

理解了原理，就能明白 Embedding 为什么应用这么广。

**语义搜索。** 传统搜索靠关键词匹配，搜“猫”只能找到含“猫”的文档。语义搜索把查询和文档都变成向量，然后找向量最接近的文档。这样搜“猫咪”也能找到“小猫”，搜“如何减肥”也能找到“控制体重的办法”。

**RAG（检索增强生成）。** 这是目前最火的应用。把知识库里的文档切成块，每块算一个 Embedding 存起来。用户提问时，把问题也变成 Embedding，找出最相似的几块文档，连同问题一起送给 LLM 生成答案。这样 LLM 就能回答它训练时没见过的私有知识。

**推荐系统。** 把用户和物品都变成 Embedding，然后找向量最接近的物品推荐给用户。用户看了“科幻电影”，系统就推荐向量相近的“太空题材”。

**聚类与去重。** 把大量文本变成向量后，用聚类算法分组，就能自动发现主题；用相似度阈值判断，就能找出重复或高度相似的内容。

**分类与异常检测。** 把文本 Embedding 作为特征输入下游分类器，比直接用词袋效果好得多。相似度异常低的样本，往往就是异常内容。

## 八、相似度计算：余弦相似度为什么常用

得到向量后，怎么判断两个向量有多相似？最常用的是**余弦相似度**。

余弦相似度衡量的是两个向量的夹角，而不是距离。公式是：

```
cosine(A, B) = (A · B) / (|A| × |B|)
```

其中 `A · B` 是点积，`|A|` 和 `|B|` 是向量的模长。结果范围在 -1 到 1 之间，越接近 1 表示越相似。

为什么用余弦而不是欧氏距离？因为余弦相似度**只关心方向，不关心长度**。在很多 Embedding 模型里，向量的长度并不携带语义信息，方向才是关键。余弦相似度能屏蔽长度差异，更稳定地反映语义相似性。

你代码里的 `calculateSimilarityByEmbedding` 做的就是这件事：先算点积，再算两个模长，最后相除。实际生产中，通常会先把向量**归一化**（长度变成 1），这样余弦相似度就退化成点积，计算更快。

## 九、影响 Embedding 质量的关键因素

不是所有 Embedding 模型都一样好。以下几个因素决定了效果。

**模型规模。** 参数量越大，通常理解能力越强。但也不是越大越好，小模型在特定领域微调后可能超过大模型。

**训练数据。** 数据质量、多样性、领域覆盖度直接影响效果。用中文数据训练的模型在中文任务上通常更好。

**向量维度。** 维度越高，能编码的信息越多，但存储和计算成本也越高。768 维和 1024 维是常见选择。

**池化方式。** 均值池化、CLS 池化、注意力池化效果不同，取决于模型训练时的设计。

**归一化。** 是否对输出向量做 L2 归一化，会影响相似度计算的稳定性。

**量化。** 你用的 `Q4_K_M` 就是一种量化方式，把模型权重从 16 位压到 4 位，大幅减小体积和内存占用，代价是轻微精度损失。对于 Embedding 任务，Q4 量化通常够用。

## 十、实践中的坑与优化

写代码时，有几个坑值得注意。

**并发死锁。** `node-llama-cpp` 的 EmbeddingContext 不支持并发调用。用 `Promise.all` 同时触发多个 `getEmbeddingFor` 会导致进程挂起。正确做法是用串行队列把调用排起来。

**缓存设计。** Embedding 计算成本不低，缓存能大幅提速。但 `Map` 缓存会无限增长，长时间运行会吃满内存。建议用 LRU 缓存，设一个上限。

**上下文长度限制。** 很多 Embedding 模型有最大 Token 限制，比如 512。超长文本会被截断，导致语义丢失。处理长文档时，通常要切块（chunking），每块单独算 Embedding。

**归一化与相似度。** 如果模型输出未归一化，而你又用点积当相似度，结果会受向量长度影响。要么统一归一化，要么老老实实算余弦相似度。

**模型选择。** 不同模型在不同语言、不同领域上表现差异很大。中文任务优先选中文优化的模型，英文任务选英文模型。多语言场景选多语言模型。

## 结语：Embedding 是 AI 理解语言的起点

回到开头的问题：机器怎么“理解”文字？答案是，它并不像人类那样理解，而是把文字变成向量，在几何空间里做比较。语义相近的文本，向量距离也近；语义不同的文本，向量距离也远。

这个看似简单的思想，支撑起了语义搜索、RAG、推荐系统、聚类去重等一大批应用。它和 LLM 共享同一套技术底座，只是输出从文字变成了向量。理解了 Embedding，你就理解了现代 AI 处理语言的第一块基石。

下次你调用 `getEmbeddingFor(text)` 时，不妨想一想：那个 768 维的向量，其实是模型在千百万次训练后，为这段文本在高维语义空间里找到的一个位置。它不生成文字，却承载了文字的意义。
