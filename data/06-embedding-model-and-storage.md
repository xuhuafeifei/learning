# 嵌入模型与向量存储

语义检索的向量这一路，选型从一开始就锁定了本地推理，不走任何云服务。

模型是 nomic-embed-text-v1.5 的四比特量化版，GGUF 格式，输出七百六十八维的向量，通过 node-llama-cpp 在进程内推理，不需要单独的推理服务。模型文件放在共享目录下的 embedding 子目录，这个位置可以被环境变量覆盖，但只允许换目录不允许换模型——维度和切词行为都和库里的数据绑死了。

启动流程上有个铁律：模型加载和下载绝不能阻塞 HTTP 端口监听。应用先起服务再旁挂异步初始化，模型没就绪期间语义查询直接返回"不可用"，字面检索不受任何影响。用户第一次启动时可能要下载几百兆模型文件，但页面照样能打开、能编辑。

切块策略是纯字符窗：每块约五百个字符，相邻块重叠五十个，保证句子不被切断后语义断裂。向量和块文本都存进 SQLite 的表里，向量列是二进制大对象；相似度计算不用任何向量扩展（没有用 sqlite-vec），就是 JavaScript 里逐条算余弦，库规模小的时候这样反而最省事。查询时先取出相似度最高的若干近邻，数量按最终要的结果数的三倍取，留出合并丢弃的余量。

失败语义也定过：向量路挂了不回滚任何东西，文档不标记为脏，下次构建照常全量覆盖，没有增量对账的复杂度。
